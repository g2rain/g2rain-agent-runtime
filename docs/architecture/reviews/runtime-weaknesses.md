## 一、总体评价

| 维度 | 现状 | 扶正后 | 说明 |
|---|---|---|---|
| 架构设计 | 优秀 | 优秀 | 分层清楚；状态模型（Redis 热态 + MySQL 兜底 + Lua 栅栏）、写操作预登记与核实、拦截器四类观测、两个扩展点都设计得当 |
| 产品思路 | 优秀 | 优秀 | “模型做决定，运行时只把关” + 执行契约 + 证据溯源 + 审批与核实，贴近企业受控执行；契约模式可独立交付 |
| 代码质量 | 良好偏上 | 优秀 | 规范一致性高；差距在核心类缺测试、状态层复杂度、少量类型丢失 |
| 评分 | 82 | 约 90 | 扶正指：关闭审计中的 P1，补齐状态层与恢复路径测试，状态层按第三节简化 |

致命问题：正常路径上没有会导致数据损坏或误执行写操作的问题。唯一可能致命的是审计 P1-8，取决于部署——如果网关把生成的 CRUD 接口开放给了租户，就可以伪造待审批参数并绕过全部校验。

## 二、产品层面的劣势

### 2.1 配置门槛高

- 执行契约规范（CONTRACT_SPEC）约 700 行，参数来源、补参、写闸、核实、抽取、实体等概念多。
- 既定立场是“不在装载时校验契约，配置正确是配置者的责任”。这意味着契约写错时，运行时只会表现为模型反复被拒、节点失败，问题不会在配置阶段暴露。
- 客户自行上手需要配套：契约模板与示例、技能编写指南的检查清单、测评（g2rain-eval）对技能的回归验证。

### 2.2 成本与延迟

一轮完整任务至少要调用 4～5 次模型：意图、技能筛选、规划、若干轮 ReAct、收口核验。节点按设计串行执行。面向价格敏感的客户时，这会是常被问到的问题。

已有的短路：单技能跳过筛选；单 REACT 技能跳过规划；单节点的结论可直接采用、跳过核验；显式恢复动作跳过意图分类。

还能做的优化（按收益与代价排列）：

| 方向 | 收益 | 代价与注意 |
|---|---|---|
| 意图分类与技能筛选合并为一次模型调用 | 省一次调用 | 提示词要重新设计，意图场景规则不能变弱 |
| 只读任务跳过收口核验 | 省一次调用 | 需要明确“只读”的判定口径（没有写目标且没有写证据） |
| 按 `ModelUse` 配置不同模型：意图、筛选、核验用小模型 | 降低单价 | 要与“模型、供应商无关”的立场一致，按配置项实现，不绑定具体模型 |
| 利用前缀缓存：ReAct 每轮重复的 system 与投影部分放在固定前缀 | 降低重复输入的计费 | 投影块的顺序和内容要尽量稳定 |
| 兄弟节点并行执行 | 只降延迟，不省成本 | `TurnScope`、`NodeScope` 不是线程安全的；写审批挂起时其他并行节点如何处理需要设计；改造代价大，优先级最低 |

## 三、架构层面的劣势：状态层复杂度

> 已并入审计文档第〇节扶正清单（0.6 批次中的状态层三步）。

### 3.1 现状

| 问题 | 表现 |
|---|---|
| 回灌口径不统一 | 任务组按 key 逐个“Redis 优先、缺了回落 MySQL”，删除与过期分不清 |
| 没有变更跟踪 | 每次 flush 都全量重写会话、实体、任务组和所有打开过的节点，量随轮次增长 |
| 编解码不对称 | 读在 `TurnSessionHydrate`，写在 `TurnFlushPlan`，`HashCodec` 只管一部分；节点空间的溢出编码放在 Hydrate 里，却由 FlushPlan 调用 |
| 收尾不原子 | 删除任务组与清空 `activeTaskId` 分两次 flush |
| 职责交叉 | `EvidenceFlow` 直接调用 `TurnFlushPlan`；`TurnFlushPlan` 还负责删除已结束任务组；持久化逻辑分散在 Hydrate、FlushPlan、EvidenceFlow、Persistence 与 6 个 Repository 之间 |

后果：后来的维护者很难一次看清全貌；审计中的 P1-2、P1-3、P1-4、P2-2 都源自这里。

### 3.2 扶正思路（不加新层次）

1. **哨兵定组**：元数据 key 是任务组的哨兵。哨兵在 Redis 时，组内 key 只读 Redis，缺失即视为空；哨兵不在时，整组从 MySQL 回灌，并记为冷恢复。冷恢复与 `lastTraceId` 非空走同一套规整：`STARTED` 证据改为 `UNKNOWN`（不论任务状态），`RUNNING` 节点回到 `READY`。
2. **按变更写入**（已完成，见 [state-refactor.md](../../design/state-refactor.md) R2）：本轮用 `FlushLedger` 记下已确认内容，flush 时对比编码结果，只写差异；对话、记录、报文仍只写新增；EXPIRE 每次照发。
3. **一个结构一个编解码**（已完成，见 [state-refactor.md](../../design/state-refactor.md) R1）：`StateCodec` / `SpaceCodec` / `GroupTtl` 成对编解码；`TurnFlushPlan` 只组装 ops，`TurnSessionHydrate` 只按哨兵规则取数。
4. **收尾一次提交**（已完成，S3-1）：persist 成功后，删除任务组、追加任务记录、清空 `activeTaskId` 与 `lastTraceId` 合进同一次 Lua 调用。

可选：任务级的小 key（元数据、断点、共享值、前情、写索引）合并成一个 Hash，key 数量减半，哨兵就是这个 Hash 本身；代价是字段需要加前缀。

实施顺序：① 哨兵定组 + 冷恢复规整 → ② 变更跟踪 + 编解码对齐 → ③ 收尾原子化（均已落地）。

## 四、代码质量层面的劣势

> 已并入审计文档第〇节扶正清单（0.7 测试要求）。

- **核心类没有单元测试**：`EvidenceFlow`、`TurnFlushPlan`、`TurnSessionHydrate`、`RuntimeStatePersistence`、`DefaultRuntimeStateFacade`、`WriteGateInterceptor`、`ParamContractInterceptor`、`DefaultNodeRunner`、`WriteVerifier`、`DefaultGraphTransitionReducer`、`TaskGraph`（调度与委派）、`PlanGraphs`、`DefaultTaskLifecycle`。审计中的 P1 几乎全部落在这些类上，这是从“良好”到“优秀”最大的差距。
- 主路径打磨充分，问题集中在恢复路径与边界条件上：说明缺的不是编码能力，而是对异常路径的系统性验证（崩溃、Redis 丢失、MySQL 失败、并发与过期组合）。建议为状态层建一组“故障注入”测试场景。

审计时没有对照你的既定决定和清单 11。最终处理以审计文档第〇节“扶正清单”为准，这里只记录口径变化：

| D-1、D-2、D-5（装载期校验、未配置工具默认只读） | 运行时不加装载期校验（R-3、R-9）；`entity` 已提供（清单 11 D-2） | 撤回；相关风险靠文档、模板与测评降低 |
| P1-1、P1-8 中“跨用户可见”的部分 | 目前只做租户级隔离 | P1-1 的“证据作用域超出依赖边”与 CONTRACT_SPEC 不一致，保留为硬伤；P1-8 按清单 11 D-22（不对外注册）撤回，留作部署核对项 |

| P2-12、P2-19、P2-22、P2-14①、P2-15 中 `EnvBuiltinTools` 与回查调 `listTools` | 清单 11 R-55、D-21、R-50、D-9；回查一条是说错了 | 撤回 |
